# ADR-0007: 错误文案国际化分层——契约码为契约，展示文案归客户端

状态：Accepted（2026-11-07 修订：miniapp 文案单源升级为 vue-i18n 双语资源，分层不变量与决策不变） | 日期：2026-11-07 | 关联 OpenSpec：identity-access

## 背景与问题

服务端 envelope 的 `message` 为英文默认文案（出自 `contracts/error-codes.ts` 注册表），miniapp
toast 直接展示该 message，中文用户在登录失败/会话终局时读到英文。是否应在后端引入
国际化（Accept-Language 协商，服务端返回本地化 message）？

## 约束与可核验事实

- `code` 是机器契约（稳定、单源、有唯一性测试）；`message` 是给人看的文本。
- message 的消费方只有三类：自家客户端 UI（中文用户）、服务端日志/对账、第三方 API 消费者
  （不存在——脚手架仅服务自家三端）。
- contracts 注册表头注已声明分层意图：「message 为英文默认文案，展示层可按需本地化」。
- web 有 vue-i18n（zh-CN + en 成对）；miniapp 文案单源同为 vue-i18n 双语资源
  `apps/miniapp/src/locales/`（zh-CN 默认 + en，键结构以 `en: typeof zhCN` 类型约束，
  键名分组与 web i18n 对齐）。
- FUNCTION_MATRIX 对国际化的承诺为「简体中文默认、英文结构可扩展」（客户端层），后端 i18n
  不在矩阵内。

## 候选方案（含现状）

1. **后端 i18n**：Accept-Language 协商 + 错误码多语言模板 + 校验消息联动。适用于公开 API
   服务第三方、服务端主动产出用户文本（邮件/短信/公告）等场景——本项目当前一条不占；
   且为每个新错误码引入多语言登记税，日志语言随请求漂移。
2. **契约层集中文案映射**：zh 文案放 `contracts`。实际消费方只有 miniapp（web 双语走自己的
   i18n 键），属为单一消费方预建共享，且与 web locale 形成同码双份中文文本。
3. **客户端持有展示文案（采用）**：web 走既有 vue-i18n；miniapp 在其 i18n 资源的
   `errors` 组维护码级映射（键 = 契约错误码 ∪ 客户端自有码 `NETWORK_ERROR`），
   未收录码回落服务端英文 message。

## 决策及理由

采用方案 3。分层不变量：**`code` 为对外契约；`message`（英文）为服务端日志/回落文本；用户
可见文案归各客户端 locale 层所有**。新错误码登记处不变（`contracts/error-codes.ts`），客户端
按需在自己的文案源补中文，无第二处强制登记点。方案 3 不是方案 1 的死路：客户端按
「本地映射优先、未知码回落服务端 message」接线后，将来若出现真实多语言 API 需求，后端 i18n
作为独立 ADR 加入即可，既有客户端不受影响。

**触发条件（届时必须重开此决策）**：P1 的通知/公告、邮件/短信等「服务端主动产出面向最终
用户文本」的能力落地时，国际化应作为该能力 ADR 的一部分决策，现在不预建。

## 复杂度、性能、兼容、测试、迁移与运维影响

- 复杂度：miniapp 新增 11 条码级映射（仅收录实际可达码）+ `showError` 一处接线；web 零改动。
- 兼容：对外 API 契约零变化；客户端 UI 行为变化仅体现为 toast 文案语言。
- 测试：miniapp 单测锁定接线行为（映射命中/未收录码回落服务端 message、终局 401 提示分类
  `sessionExpiredCategory` 的枚举结果与恰好一次提示），不断言具体文案值。
- 运维：服务端日志保持英文稳定文本，与 requestId 对账不受请求语言影响。

## 风险及撤销条件

- 风险：同一错误码在 web locale 与 miniapp 映射中的中文措辞可能漂移——属可接受的双端措辞
  差异（断言纪律本就不要求跨端文案一致）；若未来要求逐字一致，届时在 contracts 层收敛并
  修订本 ADR。
- 撤销条件：出现真实的非中文 API 消费方，或服务端主动用户文本能力立项——按触发条件重开，
  采用后端 i18n 并修订本 ADR。
