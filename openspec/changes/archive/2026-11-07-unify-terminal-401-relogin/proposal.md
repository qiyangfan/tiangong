# 变更提案：统一终局 401 客户端恢复语义（unify-terminal-401-relogin）

## 为什么变

owner 决策（2026-11-07）：修复 web 请求层的「僵尸会话」缺陷并统一跨端语义。

- **web 缺陷**：受保护请求重放一次后仍 401 时只弹过期提示，不清理会话不跳登录（清理仅发生在
  refresh 失败路径）。真实触发场景：账号被停用、权限模型变更——refresh 能成功但新 access token
  仍被实时查库的守卫（`jwt.guard.ts` 对 `!user || !user.enabled` 抛 401）拒绝，用户此后每次操作
  都重复 refresh→重放→失败→提示的循环，页面活着但不可用。
- **跨端语义分裂**：miniapp 已实现终局清理回登录，但按**错误码**判定（仅
  `AUTH_TOKEN_EXPIRED/AUTH_TOKEN_INVALID`），漏掉守卫对「无 Bearer/被停用」返回的
  `AUTH_UNAUTHENTICATED` 401。守卫的 401 有四种触发，错误码是不稳定分类，HTTP 状态码才是
  稳定契约。
- **重复提示缺陷**：终局 401 时请求层 `showApiError` 与 auth store 的过期提示（已防抖）对同一
  事件弹两条同文案消息。

## 统一不变量（两端同语义）

> 非 auth 路径（`/auth/login|refresh|logout` 之外）收到 HTTP 401 → 单飞刷新并重放一次 →
> 重放仍 401 或刷新失败 ⇒ 会话终局：清理本地凭据并引导重登。

- 判定基准统一为 HTTP 401，不按错误码分支。
- auth 路径的 401（如登录页密码错误）是操作本身的预期结果，不触发会话清理。
- 终局路径的用户提示收口给会话方（web 为 auth store 防抖提示；miniapp 为单一 toast），请求层
  不再叠加错误提示。
- **终局文案区分停用与过期**（2026-11-07 owner 追加决策；同日评审修订 miniapp 判定信号）：
  「带凭据并完成刷新重放后仍被拒」（终局位 = 实时查库拒绝，即账号被停用/删除）提示「账号已被
  停用，请联系管理员」，无凭据或刷新失败的终局提示「登录状态已过期，请重新登录」。web 端
  无凭据终局不可达，按终局码（`AUTH_ACCOUNT_DISABLED`/`AUTH_UNAUTHENTICATED`）判定等价；
  miniapp 端无凭据终局可达（凭据可能仅被系统清理而非账号停用），以是否完成刷新重放为判定
  信号，防误报停用。边界：refresh 端点按设计不泄露账号停用状态（防账号枚举侧信道），故
  「停用且 access 同时已过期」窗口期按过期文案提示，重登时由登录接口给出明确停用提示。
- silent 模式仅抑制提示，不豁免会话清理（会话死亡是导航/安全问题）。

## 契约与安全影响

- 对外 API 契约零变化；无 DB 变更。
- 用户可见行为仅在终局 401 边缘场景变化：web 由「弹提示留死页」变为「清理+回登录」，miniapp
  由「按码分支（漏 AUTH_UNAUTHENTICATED）」变为「按状态码统一处理」；正常用户不可见，安全
  方向增强（死会话不再滞留）。
- miniapp 附带行为改善：`AUTH_TOKEN_INVALID`（旧 token 结构失效）此前直接清会话回登录，现先
  尝试 refresh 重放，可恢复则不强迫重登。

## 验收标准

- web 单测：终局 401（重放仍拒/刷新失败）→ 恰好一次会话清理调用、无叠加错误提示；auth 路径
  401 不清理；silent 终局仍清理。
- miniapp 新增测试基建（vitest + uni 桩）：过期重放仍拒、被停用、无凭据、auth 路径、silent、
  恢复成功六组用例全绿。
- 全量门禁与 e2e 全绿。
