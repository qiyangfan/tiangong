# 设计：平台 AI 治理与扩展（P2）

## 1. 前置与边界

- 前置：P1 的会话/动作/确认数据模型与执行器；
- 本变更只加治理与扩展点，不改变 P1 的安全不变量（同权同审计、确认票据、幂等、可关断）；
- 仍不预置业务工具；业务仓按本契约注册，业务语义留在业务仓。

## 2. 工具注册契约

- 新装饰器 `@AiTool({ description?, risk?, maxBatch?, hidden? })`：
  - 追加 OpenAPI 扩展 `x-ai-tool`（与 `x-required-permissions` 并列），快照测试保证随契约演进；
  - 未标注的路由沿用 P1 默认分级（GET=read、POST/PUT=write、DELETE=destructive）；
  - `hidden: true` 显式排除（如内部维护接口）；
  - 服务启动时校验同一 `METHOD path` 不重复注册，缺失权限点的写操作路由直接失败（沿用授权矩阵）；
- 业务仓的「下单」等工具 = 其业务路由 + `@AiTool` 声明；平台不认识订单语义。

## 3. 风险分级与策略引擎

- 风险等级：`read` / `write` / `destructive` / `bulk`；
- 策略模型（zod 校验，存系统参数 `ai.policy`）：

| 风险        | 默认要求                      |
| ----------- | ----------------------------- |
| read        | 直接执行                      |
| write       | 执行并在会话中记录            |
| destructive | 确认票据                      |
| bulk        | 确认票据 + 批量上限 + step-up |

- 上限：单动作影响行数、单计划动作数、单会话写操作数；超限拒绝（服务端判定，模型不可绕过）；
- 策略变更即时生效：执行器每次执行前读取缓存后的策略（写时失效，与既有缓存同模式）；
- 策略配置页仅 `ai:admin-policy` 可见，后端强校验。

## 4. Step-up 重认证

- 端点：`POST /api/v1/auth/step-up`（登录态 + 密码）签发短时高权凭证（默认 TTL 5 分钟）；
- 凭证绑定用户与当前计划/动作哈希，单次使用；确认高风险动作时必须同时提交确认票据与 step-up 凭证；
- 失败（密码错误）计入既有失败锁定与审计；凭证不落日志、不入会话记录。

## 5. 多步计划

- 数据：`ai_plan`（会话、状态、创建人）与 `ai_plan_item`（顺序、动作引用）；
- 用户一次确认整份计划；确认票据绑定计划级 payload hash；
- 执行：按 order 顺序串行；任一步失败立即停止，返回已完成列表与未执行列表；
- 幂等：计划级 `Idempotency-Key` + 每步独立幂等键；
- 上限：默认单计划 ≤ 10 个动作；超限在生成阶段拒绝。

## 6. 漂移治理与门禁

- 工具目录来源于 OpenAPI；新增测试断言：
  1. 每个可用工具都能在 OpenAPI 快照中找到且带 `x-required-permissions` 或 `x-public=false`；
  2. 工具权限点 ⊆ 种子权限目录；
  3. `x-ai-tool` 的 risk 值域合法，`hidden` 工具不出现在目录；
- 快照更新脚本与工具目录快照（如有）同批更新；漂移即 CI 失败。

## 7. 可观测性

- prom-client 指标（无会话内容）：
  `ai_messages_total{outcome}`、`ai_tool_executions_total{risk,outcome}`、`ai_tokens_total{type}`、
  `ai_confirmations_total{result}`；
- 标签基数控制：工具名采用注册名（有限集合），不携带参数或用户标识；
- 日志：会话 id、动作 id、toolName、requestId、错误码；不写提示词与工具结果正文。

## 8. 多端入口

- 小程序：`uni.request` 不支持流式 SSE，消息端点支持 `stream=false` 轮询模式；轮询只改变传输，
  服务端策略、确认票据与 step-up 要求完全一致；
- 小程序确认 UI 同样提交服务端票据；客户端本地确认不生效；
- 入口按钮受 `ai:chat` 控制（展示层），后端强校验。

## 9. 评测与回归

- 确定性 fake provider 场景文件（JSON）：工具选择、风险分级、批量超限、step-up 缺失、多步部分失败、
  注入样例；`pnpm test:ai-eval` 无网络运行并进门禁；
- 修复/新增策略规则必须同步增加评测场景（测试同步原则）。

## 10. 迁移与回滚

- 迁移：新增计划表与 step-up 存储；`ai_action` 增加可空 `planId`（兼容 P1 数据）；
- 回滚：停用 AI 开关即可止血；数据库回滚 = 删除新增表/列，P1 数据不受影响；
- 兼容：策略参数缺省时使用默认分级；未配置 step-up 时不启用该要求（记录告警）。

## 11. 备选方案与否决理由

- 策略写死在代码：否决——不同业务风险不同，配置化才能落地；
- 由模型自评风险：否决——不可信；
- 客户端确认代替服务端票据：否决——可被绕过；
- 为多端各写一套编排：否决——语义分叉，违背同权同审计。
